# emerald

This is emerald's handbook, for whoever works on it: what every part does, how it is built and how it is tested; `README.md` at the root of the repository is the page for a person who installs it. Desktop app for running and supervising several Claude Code sessions at once on Windows ARM64. The design and the milestone list, the record of what each milestone and fix batch produced, the backlog of asks not yet planned, the hardening passes and the project's first brief are kept in the working repository and are not part of the published code; `docs/WHATS-NEW.md` is the short record of every batch.

## Layout

- `packages/shared` protocol, session, layout types and limits
- `packages/daemon` `emmerd`: owns PTYs, scrollback and sessions, serves clients on `\\.\pipe\emmerd-<user>`, a pipe per Windows user and, when `EMERALD_HOME` names another home, per home (fix 495)
- `packages/app` Electron app: pixels and keystrokes only
- `packages/cli` `emerald`: command line client for the daemon, for scripts and for Claude sessions supervising each other
- `demo` the template of the demo repository and the script that creates or resets it (see Demo)

## Commands

Requires Node 24 or newer. No native compile step: node-pty ships a win32-arm64 prebuild.

```
npm install
npm run build              compile shared, daemon and cli
npm test                   node:test suites
npm run typecheck -w @emerald/app   the app's three projects: the main process and preload, the renderer, and the renderer's tests and models (fix 405; electron-vite typechecks none of them)
npm run smoke              start emmerd if needed, spawn a shell over the pipe, run dir, kill
npm run dev -w @emerald/app  launch the app with hot reload (starts emmerd if nothing owns the pipe)
```

The daemon keeps running after the app closes so sessions survive a UI restart. Logs are in `~/.emerald/logs/emmerd.log` (the window's own in `main.log` beside it, moved aside to `main.1.log` past 8 MB at a start, fix 559), and the hooks every Claude posts in `~/.emerald/logs/hooks.jsonl`, each line's `tool_input` and `tool_response` cut to their first kilobyte with a `truncated` mark and a status line reduced to the fields the activity reads (fix 377; `EMERALD_HOOKS_FULL=1` keeps whole payloads), the file rotated to `hooks.1.jsonl` past 64 MB at the daemon's start and streamed line by line at the load, the `activity log loaded` line saying every generation file's line count and the milliseconds, and the earliest line's time as `oldest`, which the activity view shows as `history from <date>` under its header and `emmer activity` as its last line (fix 607, level 59). The older generations (`hooks.1.jsonl` and up) keep only what the activity view reads, slimmed at the rotation, and as many of them are kept as fit in 192 MB; a generation with full payloads found at a start is slimmed in place, so a backup copied into `logs` as the oldest generation, with the daemon stopped, is history kept (fix 629). A SessionStart under another conversation than the one a session is bound to is ignored, and `emmerd.log` says so once per new conversation, naming the pane's session, the bound id and the new one, with the hint that it is a nested `claude` or a new conversation with no SessionEnd before it, which `emmer explain` shows (fix 734). `~/.emerald/daemon.json` holds the running daemon's pid and the pipe token every hello presents; a window that finds no file on connecting waits up to 30 s for it before its hello (fix 632). `~/.emerald/state.json` holds the layout tabs and `~/.emerald/sessions.json` the session list; after a daemon restart the old sessions are listed as exited and can be resumed in place (`claude --resume` for a Claude session that reported in, a fresh shell or Claude otherwise). Because the daemon survives, an upgraded app can find itself on a daemon from the previous build; the window then shows a banner naming it and offering Restart emmerd, which kills it and starts the shipped one, with the sessions coming back as exited.

Hooks: `emmer hooks install|uninstall|status` merges emerald's command hooks into `~/.claude/settings.json` (or `CLAUDE_CONFIG_DIR`'s `settings.json` when that is set) next to any other tool's entries (`npm run hooks -w @emerald/daemon -- install` still works as an alias). Since fix 725 Emerald's own Claude sessions also load the emerald mod (`--plugin-dir` on the launcher's command line, the folder `cli/mod` beside the CLI), a Claude Code plugin whose one hook posts every hook event but PreToolUse from inside the Claude process, with no `cmd.exe` or `curl.exe` started per event; the hook file stays installed as the fallback (a Claude Code older than 2.1.287, `--safe-mode`, `disableAllHooks`, an organisation that allows only managed mods, a Claude you start yourself, or `EMERALD_CLAUDE_MOD=0`), the daemon keeps the first of the two copies of an event and folds the other, and the main log says once per session when every post came from the hook file. `emmer hooks status` says whether the mod is shipped (fix 726), never whether it loaded, which only a session knows, and the mod counts nothing toward complete. The app checks the same status when its window opens and shows a banner with an Install button while anything is missing; it runs the shipped CLI to install, so there is one installer. Since fix 606 the window watches Claude's settings file while it runs, so the banner rises and falls as the hooks come and go without a restart, says so when another program keeps rewriting the file rather than offering Install again, and has a Test button that sends one event through the installed hook to the daemon (`hooks.test`); `emmer hooks status --test` does the same from a terminal. `{"promptHooks": false}` in `~/.emerald/config.json` turns the banner off. The installer also sets Claude Code's status line. Claude Code hands its status line command JSON after every turn with the model and how full the context window is, and nothing else carries either, so the installer puts a small wrapper of its own in the single `statusLine` slot: `claude-statusline.cmd` under `~/.emerald/hooks` runs `claude-statusline.js` on the same Node the installer ran on (the app's own `Emerald.exe` once installed), which posts the JSON to the daemon and then runs whatever status line was in the slot before, kept in `statusline-previous.json`, with the same JSON on its stdin and its output passed straight through, so a status line you already had still shows. The post finishes before the previous command starts, and the previous command runs under the shell Claude Code would have run it under, which on Windows is Git Bash (`CLAUDE_CODE_GIT_BASH_PATH`, else the `bash.exe` beside the `git.exe` on PATH, else `cmd.exe`), since a status line another tool installed is written for bash: Orca's is an `if [ -z ...` one-liner that `cmd.exe` cannot parse, and run beside the post under `Emerald.exe` as node that failure starved the post, which is why the model and context fill never showed on an installed app before M34. `emmer hooks uninstall` puts the previous one back, and `emmer hooks status` says whether the slot is ours and which version of the wrapper script is installed beside the shipped one. An install from before this counts as stale, so the hooks banner offers the upgrade. The installer also lands the `emmer-cli` skill, a `SKILL.md` in `~/.claude/skills/emmer-cli` (the skills folder beside the settings file), so every Claude Code session on the machine knows when to reach for `emmer` and how: the commands, the two kinds of read, waiting on a state rather than polling, `prompt` for a handoff that wants the reply back, `explain` when a state looks wrong, and writing a checkpoint at each phase change. `emmer skill` prints the same text, so the guide always matches the CLI; `hooks status` counts a missing or hand-edited copy as incomplete and the banner offers the reinstall; `hooks uninstall` removes it and leaves the other skills alone. Since fix 710 `emmer hooks status` also names every hook and status line command in Claude's settings that points at a file no longer there, each marked as emerald's (a path ending `/hooks/claude-hook.cmd` or `/hooks/claude-statusline.cmd`, an old home's say) or another tool's; `hooks install` takes emerald's dead ones out and leaves another tool's alone, and since fix 733 `hooks uninstall` does the same, so removing Emerald leaves no dead entry of its own, and only emerald's count against complete, so the banner rises for them with a Fix button that runs the install, and names another tool's without offering to touch them.

A session remembers the arguments it was started with (`emmer new <dir> -- --model opus`, or the dialog's args box) and the last conversation it hosted: its id, the folder Claude was started in and, for a Claude session, the args, kept through Claude leaving, the exit and a daemon restart. A resume picks that conversation up: a Claude session comes back in that folder with the same args and `--resume <id>`, and a shell that ran `claude` by hand comes back as a shell in the folder Claude was started in with `claude --resume <id>` typed at its first prompt, so the pane is a shell again when Claude exits, as it was (a shell that shows no prompt within ten seconds gets nothing typed, and a conversation folder that is gone falls back to the spawn folder). A session with no conversation behind it resumes as a bare shell in its spawn folder. The Resume button's tooltip says which it will be. Since fix 159 a pane on an exited session shows the last screen the session had: the daemon keeps every live session's frame when it is asked to stop (`daemon.stop`, which `emmer daemon stop` and the app's Restart ask before falling back to a kill, since a killed process keeps nothing) and a session's own frame when its PTY ends, on the record in `sessions.json`, and the pane draws it dimmed under the exited title until Resume, when the new process starts over; `emmer explain` prints the kept rows and `emmer read --screen` marks them kept. A daemon that took the stop exits within two seconds whatever a client still holds open (fix 164), its record unlinked first. Typing or pasting into such a pane sends nothing (the daemon has no process to give it to) and shows a notice over the kept frame, `exited`, `This session's process has ended; its last screen is kept.`, with a Resume button, fading four seconds after the last key, on a click in the pane, or when the session comes back (fix 313); nothing shows from the exit itself, so the frame stays readable.

A session is named after the folder it is in until you rename it, and after Claude's conversation title once it has one: when Claude Code names the conversation (its own summary after the first turn, or `/rename`) the row and the pane title follow, and go back to the folder when Claude leaves; before that a Claude session that changes directory takes the new folder's name, a shell that runs `claude` in another folder takes that folder's name the moment Claude starts, and a plain shell reports every `cd` through its prompt (the launcher wraps your prompt function so it also emits the OSC 9;9 sequence Windows Terminal uses; a shell started with `-- args` of its own keeps its spawn folder, since the wrapper needs `-Command`). ## Attention

When a session goes to needs-input, done or errored, its sidebar row pulses between its own ground and the badge colour, and so does the title bar of any pane showing it, with a ring in the same colour around that pane, and the layout tab holding that pane, on show or not; all of them run on one clock, so a title that appears later than its row still beats with it. The pulses sync by name on one pass over the document's animations, run when a pulse starts or its attributes change (fix 729), no longer on every change to the page. Since fix 206 the pane's whole ground breathes too, from transparent to a fifth of the state's colour on the same clock as the ring, which now rides in the same keyframes, so a wanting pane among six is the first thing the eye lands on while the terminal's text under it stays crisp (20 %, judged on a six-pane frame; 15 % was a hint the ring outdid and 25 % added little at the ceiling); it stops with the ack and is off under `prefers-reduced-motion`, where the ring alone runs. A change from one of the three states to another counts again, so a question after a finished reply nobody has clicked away chimes and pulses in the new colour. The pulse runs until you click that session's pane or its sidebar row, or press a key with its pane focused (fix 189; until then a click or a key anywhere silenced every pulse in the window, and with eight panes on a tab nobody could tell which one had wanted them), and that click is also how a done session is seen: its badge goes from done to idle at the same moment, with the reply still on the row's bottom line. A press that names no session, on the tab strip, the rail or a key that switches tabs, acks nothing and hushes every chime instead, so a click on a pulsing layout tab keeps the rows and the pane titles pulsing while you look for the one that wanted you, with no beeps flying around meanwhile, and a done row already there when the window opened clears only by a press on it (a done session in the focused pane is seen at once only when you clicked or pressed a key in the last ten seconds; a reply into a pane nobody has touched pulses and chimes like any other). A chime plays when it happens and every four seconds after, so you can look away from the screen and still know, and the taskbar button flashes with it and wears a badge with the count of sessions wanting you, breathing at the sidebar's rate, until the click that clears the pulse (fix 104: whenever it would chime it flashes, so the chime's setting governs both; under a private `EMERALD_HOME` both are held to the log, so a test run never flashes your taskbar). The speaker button at the bottom of the sidebar cycles the chime through repeat, once and off (the pulse stays in every setting) and the choice is remembered. The real chime belongs to the real home: an app running under a private `EMERALD_HOME` (every verify script's, and a click-through's) is muted, and plays a different, lower chime when `EMERALD_CHIME` is set in its environment, so a beep from a test window is never taken for your own; the speaker button's tooltip says which. Such a window posts no Windows notification either: the line goes to the app's log instead (`notification held under a private EMERALD_HOME`), unless the run asked for a notify file or set `EMERALD_NOTIFY_ALWAYS`. A session already done when the window opens does not pulse: only a change you could have missed does. A session that goes `waiting` does not pulse or chime: its turn ended only because a background task is still running, and the `done` that follows the last one pulses as usual. Ctrl+Shift+A (prefix `a`) takes the focused pane to the session that has waited longest (fix 201: needs-input first, then done, then errored, oldest first), a second press within four seconds takes the next in that order and comes round at the end, none of the presses acking what they show (a look-first key, like a tab switch), and with nothing waiting the corner of the window says `Nothing is waiting` for two seconds; the jump palette lists the waiting sessions first in that order with the wait after the state word, `needs input 4m`. A press on the speaker button is the one click that does not acknowledge, and neither is a press in the menu it opens. A working session that has posted no hook for longer than its own turn's pace (three times the median gap between its tool calls this turn, floored at ten minutes; `EMERALD_STALE_AFTER_MS` sets the floor for a script) is quiet (fix 232, the `!` beside the name until then): the row and the title pulse in the muted tone, never the needs-input teal, the badge reads `quiet 12m` with the threshold it tripped in its tooltip, the chime and the notification come as for the other states, Hush holds the pulse without the chime, and the next hook clears it; `emmer wait --for stale` returns when the daemon flags it, `emmer ls` prints the word in the state column and `emmer explain` names the threshold, and the emmer-cli skill carries a watchdog routine (poll `ls --json`, read the screen with `emerald screen`, nudge with `emmer send`, then kill) so a supervising session acts before anyone hears a beep. `/demo-solo quiet` runs one tool call that hangs past the floor.

A question that arrives in the pane you are answering stays quiet (fix 701): when the session asking is in the focused pane and you clicked or typed in that pane in the last ten seconds, there is no chime, flash, notification or pulse, since you are looking at it; the badge still says needs input. The window's own mousedown and keydown feed the read, per pane, so a scripted lift of the shade does not count. A pane hidden by Focus (the zoom) that wants you pulses its layout tab, the tab on show included (fix 702), and a click on that tab undoes the Focus with the focus kept on the pane that was zoomed, so the pane asking comes into view.

When the window is not focused, the same moment also posts a Windows notification with the session's name and its badge, and for a finished turn the first line of the reply; a click on it brings the window up and shows that session in the focused pane, which acknowledges it. A session posts at most one every five seconds, so a permission prompt right after a turn's end does not post twice. Right-click the speaker button for the menu: the chime setting by name, and Notifications on or off, remembered with the sound. A pulsing row carries a crossed speaker at its right end while the chime is set to repeat (fix 190, where Resume sits on an exited row): Hush stops the chime for that one and keeps the pulse, so you can stay where you are and still see it wants you; the button dims while hushed and a second press unhushes, Hush and Unhush are on the row's menu too, a new arrival is never hushed and chimes as before, and an ack empties the hush with the pulse. Mark unread on a sidebar row's menu (right click, or the row's menu button) puts the row back to pulsing with no chime and no notification, for a session you want to come back to; it stays until the next click or key, or the next change of state, and it is greyed while the session is working; a done row marked unread after the click that saw it is idle by then and pulses green all the same.

## CLI

`node packages/cli/dist/main.js` after a build, `emerald` once `node_modules/.bin` is on your PATH, or `emmer` from any terminal after installing the app (see Packaging and installing). Sessions are addressed by id, by name or by a unique id prefix. Exit codes: 0 done, 1 failure, 2 `wait` or `prompt` timed out, 3 `prompt` sent the text and the session never started working, 64 bad usage.

```

                                                 send --enter and wait in one, the reply's first line back
```

Two ways to read a session. The stream (`read`, the default) is what the session emitted over time with the escapes stripped, so a program that repaints a line, a shell's prompt, a progress bar, a TUI, reads as the sequence of things drawn: a `clear` typed keystroke by keystroke can come back as fragments, and the spaces a prompt draws by moving the cursor are absent. The screen (`read --screen`) is what a terminal shows now, rendered by a headless xterm in the daemon fed the same bytes. A supervisor checking on a TUI, a Claude session in particular, wants the screen. To follow a session over time, take the `nextCursor` from one read (`--json` always has it, text prints it when `--cursor` was given) and pass it as `--cursor` to the next: only what was written after it comes back, and `oldest` says when the scrollback had already dropped some of it. `wait --for tui-idle` resolves once nothing has been written for 1.5 s (`--quiet-ms` changes it) and `--for exit` when the process ends, with the exit code; both work on any program, hooks or not, where the state names need Claude's hooks. An exited session counts as quiet.

`prompt` is `send --enter` and `wait` in one, with two gates from herdr's `agent prompt`: a session that needs input is refused (exit 1, saying what it is asking), since the text would land as the answer, and `--force` sends anyway; after the send the session has five seconds to go `working`, else the command exits 3 as stalled, since the text is most likely sitting in the input box (`read --screen` shows it); then it waits for the turn to end, `--timeout` as `wait`'s, and prints the first line of the reply, or `needs input: ...` when the turn ended in a question, or the error when it errored (exit 1). A session already working is taken as moving, and M30's `waiting` counts as still working. `explain` is for the moment a row looks wrong: the session's name, kind, state and how long it has been there, the sentence behind the badge, the Claude session id it is bound to, the last prompt and reply, then the last N of its hook events (`--lines`, 20 by default) from `~/.emerald/logs/hooks.jsonl`, oldest first, each with the time, the event, whether it was applied (`ignored-agent` a subagent's, `ignored-foreign` a nested `claude`'s with its session id, `unknown-session` a hook from a session the daemon does not know) and the state change it made, which the daemon now writes on each line. A shell's `command` line says what its last command did (`running 40s`, `failed (3) 2m ago`, fix 196) and a `touched` line lists the last files the session wrote (fix 198). It reads the log directly, so it works with `emmerd` down; the session then comes from `sessions.json`, where an exited one has its exit and a live one is said to have been live when the daemon last wrote the file.

Set `EMERALD_HOME` and `EMERALD_PIPE` to point the CLI and a daemon at a private home and pipe; `EMERALD_DAEMON_MAIN` or `--daemon-path` tells an installed CLI where `emmerd`'s `dist/main.js` is. `EMERALD_INSPECT_PORT=<n>` puts the app window's devtools server on that port (fix 355), so the installed build can be attached and profiled over CDP the way a test harness window is; the main log says `inspect port <n> on 127.0.0.1`, or why it was refused, and the renderer's console warnings and errors reach `~/.emerald/logs/main.log` as `renderer: <level> <message>` lines, five a second at most. A CLI command that fails prints one `emerald: <message>` line on stderr whatever failed (fix 379): a pipe that drops mid-request settles every pending request with the error, an uncaught error is written as that line, and a run about to exit 1 having printed nothing says `emerald: exiting 1 with nothing to say`, so the next silent exit names itself.

## Packaging and installing

`npm run dist -w @emerald/app` builds `packages/app/release/Emerald-setup-<version>-arm64.exe`, a per-user one-click NSIS installer (about 106 MB, no admin rights). It installs to `%LOCALAPPDATA%\Programs\emerald`, adds `resources\bin` to the user PATH so `emmer` works in any terminal opened afterwards, and puts a shortcut in the Start menu and on the desktop. The installer also registers emerald as an opener for `.md` and `.json` under the user's own hive (fix 342: it appears in Windows' "Open with" list and a person picks it there once if they want it; a default already chosen stays; since fix 381 the entries are written by `build/installer.nsh` itself and never as the extension's default, where electron-builder's own block had put them, and the uninstall clears a default that names emerald and nothing else), and a file opened that way, or `Emerald.exe <file>` by hand, lands as a pinned tab in the running window, the launch itself exiting at once (a second launch with no file still opens a second window). Uninstalling from Settings, or `"Uninstall Emerald.exe" /S`, removes the files, the PATH entry and the two registrations, and runs `emmer hooks uninstall` through the installed shim, which takes Emerald's hooks out of Claude Code's settings, puts the previous status line back and removes the `emmer-cli` skill; the call runs on a real uninstall alone, never on an update's uninstall of the old build, and its exit code is ignored so a settings file it cannot parse never stops the uninstall (fix 630; an Emerald older than 0.1.620 leaves the hooks behind); `~/.emerald` is left alone. The installer itself does not write Claude Code's settings; the app offers to install the hooks the first time its window opens without them. The version is `0.1.<first fix id of the batch it came from>` since fix 239, bumped at every batch's docs commit, so `emmer --version` and the app menu's `What's new` hint say which batch a build is. An installed build checks for a newer one (fix 239, `electron-updater` with the generic provider) at launch and every four hours against `http://127.0.0.1:7420/latest.yml`, the feed folder `emmer feed publish` fills from a `dist` and the daemon serves when it exists (fix 240; `emmer feed serve` is for a box with no daemon) (`EMERALD_UPDATE_URL` overrides the URL, `EMERALD_NO_UPDATE=1` turns the check off, a dev build never checks); when the feed is ahead the installer downloads on its own into `%LOCALAPPDATA%\emerald-updater` with nothing on the badge while it does (fix 625; before it a first click on `0.1.240 available` started the download, and the badge read `downloading 0.1.N` and then `downloading 37%`, fix 296), and once it is ready a badge at the right of the title row reads `Restart to update`, its tooltip saying what a restart does to the panes; a background download that fails reads `Retry <version>` (fix 656; `<version> available` before it), and a click on that tries again with the progress on the badge as before; the one click on `Restart to update` closes the window, stops the daemon with its screens kept, runs the installer silently and relaunches, and the new build's first launch starts the new daemon and runs `emmer hooks install`, every pane coming back through Resume; that click also posts a notification, `Installing emerald 0.1.N`, `The window closes now and comes back on its own in about a minute`, and leaves `installing.json` under the emerald home, so an emerald started in that minute by hand says `Still installing emerald 0.1.N, about 40 s to go` and quits with no window and no daemon rather than coming up as the old build (fix 282; a marker at the build's own version, or older than three minutes, is deleted and the launch goes on). Nothing installs until that click (fix 239's rule, kept by fix 625); `emmer update` prints the updater's state off the daemon, `--check`, `--download` and `--install` make the badge's clicks from a pane (`--check` now ends on `ready` when the background download finishes inside it) (fix 271, level 49, so it works once the new daemon is up), and a batch that runs unattended installs itself with the last of them. Nothing installs on its own. The build is unsigned, so no signature is checked, and a file the updater downloaded itself carries no mark of the web; the first real update through the feed is the batch after fixes 228 to 239, since the build those replace has no updater and installs by hand.

How the install is laid out: `scripts/stage.mjs` copies the built daemon and CLI, their `node_modules` (`@emerald/shared`, the win32-arm64 node-pty prebuild and the headless xterm behind `read --screen`) and `bin\emmer.cmd` into `packages/app/stage/`, and electron-builder ships that directory under `resources\` next to `app.asar`. ## Troubleshooting

A Claude session in a pane that is nearly all white, where the same session in Windows Terminal has its orange and yellow, means the daemon was started from inside a Claude Code session before M34 and handed its `NO_COLOR=1` to every pane; the daemon now strips what describes the terminal it was born in (`NO_COLOR`, `FORCE_COLOR`, `CLICOLOR`, `CLICOLOR_FORCE`, `TERM_PROGRAM`, `TERM_PROGRAM_VERSION`, `WT_SESSION`, `WT_PROFILE_ID`, `CLAUDE_CODE_SESSION_ATTENDED`) and sets `TERM=xterm-256color` and `COLORTERM=truecolor`, so restart it from a plain terminal (`emmer daemon stop`, then `emmer daemon start`, or Restart emmerd from the app's banner) and resume the sessions, since a session keeps the environment it was started with. No model or context fill on a Claude row, with `hooks.jsonl` showing no `StatusLine` events, means the status line wrapper is from before M34; `emmer hooks install` rewrites it, and `emmer hooks status` shows the wrapper's version. A Windows Terminal window titled with node's path that flashes when a session closes, or stays open showing a launch error, was node-pty's console-list helper getting a console of its own from a daemon that has none; since M9 fix 35 the daemon forks it hidden.

Ctrl+V pastes in any pane (fix 92), and a Ctrl+V sent with no key code, as Wispr Flow's dictation sends its paste, pastes too (fix 637), as it does in Windows Terminal: the clipboard's text goes through xterm's paste (bracketed when the program asked for it, as Claude Code does, so a multi-line paste lands as one paste and not as lines run), and when the clipboard holds an image and no text the raw Ctrl+V byte goes through instead, since Claude Code reads the image from the clipboard itself on that byte, which keeps image paste working where an intercepting terminal breaks it; Ctrl+Shift+V pastes as before; in the chat box an image goes in as a file path, which Claude Code takes as an image (fix 721). Shift+Enter in a pane running Claude is a newline in the prompt box, not a submit: Claude Code takes the kitty keyboard protocol's Shift+Enter (`CSI 13;2u`, what its `/terminal-setup` teaches VS Code and iTerm to send) and the pane sends that sequence while Claude is what is running, from the moment it reports in until it leaves. A plain shell keeps getting Enter, since PowerShell has no use for the sequence and would echo it, and Ctrl+Enter and Alt+Enter are left to xterm.

Ctrl+Shift+C copies the selection in any pane and does nothing without one (fix 441, Windows Terminal's key; Ctrl+C still sends ^C), and a right-click copies the selection and clears it, or pastes when nothing is selected, through the same path Ctrl+V takes; the right-click also opens the pane menu as it always has, both on purpose (kept so by the user at the batch of fixes 426 to 449). Copy on select, off by default, is a check item on every pane's menu, under Close pane and above the colour schemes (fix 491, moved from the shade button's menu). In a program that takes the mouse, Shift+drag selects. Since fix 538 the right button's press and release never reach the program, even one that takes the mouse as Claude Code does, so a right-click there copies or pastes once, as it does in a shell, and a Shift+drag selection is copied rather than the old clipboard being pasted over it.

The terminal's colours are a scheme (fix 225): the sixteen colours plus background, foreground, cursor and selection in the shape Windows Terminal's `colorSchemes` uses, since that is the file people already have. The app ships six under `packages/app/resources/schemes` (`emerald`, the amber, teal, green and red of the chrome as they have been since M38, `emerald gem`, the Emerald skin's default (fix 572), plus Dracula, Solarized Dark, One Dark and Tokyo Night from their published palettes; `stage.mjs` copies the folder under `resources\` with the daemon), and reads your Windows Terminal `settings.json` (the packaged, preview and unpackaged paths under `%LOCALAPPDATA%`, or `EMERALD_WT_SETTINGS`) for yours, listed under their names after the shipped ones, through a main-process `schemes.list` that reads both on the worker's `fs/promises` at each ask and never writes. The pick is the last section of a pane's right-click menu, `Colour scheme` with one checked row per scheme, one scheme per window kept in localStorage as `emerald.scheme` (unknown or missing falls back to the skin's default, `emerald` under Classic and `emerald gem` under Emerald; a pick of the skin's own default stores nothing and follows the skin), applied to every terminal at once through `term.options.theme`, and the pane's ground takes the scheme's background so a light scheme does not sit in a dark frame. Since fix 244 a session can carry its own scheme (kept on its record on the daemon, level 46, so it follows the session to any pane and across a restart, `emmer set --scheme <name>` and `--clear-scheme` from the CLI), the terminal resolving the session's scheme if set and on the list, else the window's; each `.term-host` carries its own ground. The `This session only` toggle and its `emerald.schemeScope` key are gone. The chrome's tokens do not move; a light chrome is a later batch.

## Acceptance scripts

`packages/app/scripts` drives the built app over the Chrome DevTools Protocol. Build first (`npm run build`, then `npm run build -w @emerald/app`), run one at a time. The window a script opens is shown without focus and past the right edge of every display, and on an Electron profile of its own under the run's `EMERALD_HOME` (`--user-data-dir=<home>/electron-profile`, fix 115, removed when the harness stops unless `EMERALD_KEEP_PROFILE` is set), so two scripts launched together never fight over one cache and the user's own profile is never touched (`EMERALD_WINDOW=background`, which the launcher sets: the x is the rightmost display's edge plus 50, there is no taskbar button, and the app logs where it put the window and puts it back if Windows moves it, as it does when a display goes away for a moment), and the page is told it has focus over the protocol rather than being brought to the front, so a run beside your own emerald neither covers it nor takes the keyboard, its chime is muted and its notifications go to its log (see Attention):

To run one of these while your own emerald is open, point it at a private home and pipe first; the app, the daemon and the scripts all honour both:

```
$env:EMERALD_HOME = "$env:TEMP\emerald-verify-home"; $env:EMERALD_PIPE = '\\.\pipe\emmerd-verify'
```

Without that, a script's fresh-state step deletes `~/.emerald/daemon.json` and its clean-up stops your daemon.
